Exercise each finding's logic (vulnerable vs fixed). Infrastructure findings show detection evidence instead of a control.

What this is & where the logic comes from

This console reproduces the decision logic of the ChattyBot / "Ask Narelle" LLM course chatbot, transcribed from its public source (github.com/chinannong/ChattyBot, commit e4d40af). The access-control checks are direct ports of the real lines — for example F-01 is "ntu.edu.sg" in email[-10:] from Home.py L168, and F-03 is the literal "Ong Chin Ann" in user check at L264. A companion Python harness runs the sign-in block verbatim (Home.py L104-200) under automated tests. Service outputs shown here (stack-trace text, cost figures, model replies) are illustrative stand-ins, because a browser cannot run Python, Azure or a live LLM. Simulation only — not the live system; no network, no real accounts.

How the vulnerabilities were identified

Only steps 03 and 04 are application failures. Azure's filter (02) worked; the unhandled error leaked the trace, which led to the public repo and the full finding set.

Logic mode
Interactive cards reproduce the decision logic from the public repository (commit e4d40af). Supply-chain cards report detection checks (pip-audit, grep, file). Proving a check is bypassable is not the same as entering the live service, which needs authorised testing by the system owner and NTU IT security.
